## 1. Summary of Changes

### CS-018: Static Resolution Scope & Inheritance
- **Lexical Scope Hierarchy:** Implemented upward lexical scope search `_enclosing_scope_ids` in `RelationshipResolver.resolve_calls` to correctly resolve local and nested helper functions to their enclosing definitions.
- **Base Class Method Resolution:** Implemented recursive base class method resolution `_find_class_methods` and `_find_base_class_nodes` for `self` and `cls` attribute calls across single and multi-level inheritance hierarchies.
- **Multi-dot Attribute and Module Paths:** Added support for resolving multi-dot imports and class references (e.g. `pkg.base_mod.Component`).
- **No Dynamic Execution:** Preserved strict static analysis rules; project code is never imported or executed.

### CS-019: Type Stub (.pyi) Symbol Resolution & Fallback Ordering
- **Stub Shadow Filtering:** Implemented `_filter_stub_shadows` in `RelationshipResolver` which prioritizes `.py` implementation nodes over `.pyi` type stubs when both are present for the same qualified name or module.
- **No False Ambiguity:** Prevented `.pyi` type stubs from triggering `ResolutionStatus.AMBIGUOUS` duplicate collision diagnostics when shadowing corresponding `.py` source implementations.

### CS-008: Options, Metrics Flag, and Cache Key Semantics
- **Policy & Builder Flag:** Added `compute_metrics: bool = False` to `AnalysisPolicy` and `build_graph(parsed, compute_metrics=...)`. When `compute_metrics` is `False`, nodes retain raw structural attributes without metric enrichment.
- **Cache Isolation:** Added `metrics: policy.compute_metrics` to `policy_fingerprint` in `codestruct.storage.cache_keys`, ensuring analyses with `metrics=false` and `metrics=true` generate distinct cache keys and isolated cache entries.
- **API & Worker Integration:** Enabled `options.metrics: bool` in `POST /api/v1/analyses`, `AnalysisService.create(...)`, `SpawnJobExecutor`, and `run_analysis_worker`. Custom pattern options (`include_patterns`, `exclude_patterns`) and `source_grammar` remain safely validated and rejected with HTTP 400 `OPTION_UNSUPPORTED`.

### CS-010: Metric Computation Semantics, Module Metrics, and Iterative Cycle Detection
- **Strict Dependency Coupling:** Refined `fan_in` and `fan_out` to count only resolved dependency relationships (`IMPORTS`, `CALLS`, `INHERITS`, `CONSTRUCTS`, `REFERENCES`), explicitly excluding containment edges (`DEFINES`, `CONTAINS`, `MEMBER_OF`) and self-loops.
- **Iterative Tarjan SCC:** Replaced recursive Tarjan's SCC in `DefaultAlgorithmAdapter` with an explicit stack-based iterative algorithm, eliminating Python recursion depth limits on deep call trees (verified up to 1000+ deep node cycles).
- **Self-Loop Detection:** Added explicit tracking and reporting of self-loops on dependency edges (`in_cycle = True`).
- **Component vs Community Distinction:** Separated reachability connected components (`component_id`) from deterministic Clauset-Newman-Moore greedy modularity community clusters (`community_id`).
- **Module Architecture Metrics:** Implemented module-level metrics ($C_a$, $C_e$, module instability, cohesion over contained entities, and relational density).

### CS-009: Transient NetworkX Algorithm Adapter & Parity
- **Port Conformance:** Implemented `NetworkXAlgorithmAdapter` conforming to `GraphAlgorithmPort`, building a transient `networkx.DiGraph` to compute degree centrality, in/out degrees, strongly connected components, connected components, and greedy modularity communities.
- **100% Adapter Parity:** Verified 100% numerical and community partition parity between `DefaultAlgorithmAdapter` and `NetworkXAlgorithmAdapter` across all test corpora and probes.
- **Port Selection & Fallback:** Declared `networkx>=3.0,<4.0` in `[project.optional-dependencies] metrics`. `get_algorithm_port()` uses NetworkX if installed and cleanly falls back to `DefaultAlgorithmAdapter` when missing.
- **Zero Object Leaks:** NetworkX objects remain strictly encapsulated inside the metrics adapter layer and never leak into storage, serializers, or API schemas.

### CS-011: Canonical Explanation Context Extraction
- **Canonical Schema Support:** Updated `extract_node_context` in `codestruct.analysis.llm_summary` to prioritize canonical flat `location` (`path`, `start_line`, `end_line`) and parse canonical `attributes` lists/dicts (`centrality`, `community`, `component`, `fan_in`, `fan_out`, `in_cycle`, `instability`, module metrics).
- **Bounded Evidence Context:** Added bounded static evidence references (`id`, `origin`, `observation_kind`, and `path:start_line-end_line`) into the explanation prompt.
- **Uncomputed vs Zero Metrics:** Updated `RuleBasedExplainer` to distinguish uncomputed metrics (analyses run with `metrics=false`) from computed zero metrics (`fan_in=0, fan_out=0`), providing truthful connection narratives without synthesizing fake metrics.
